## 一、功能概述

登录用户凭 Access 令牌发布问题：填写标题（1–100 字）与正文（1–5000 字），标题/正文为自由文本（strip 规范化后非空）；author_id 只取自令牌中的当前用户，绝不取自请求体。未登录访客一律 401 且不创建数据。

接口：`POST /api/v1/questions`（201 / 401 / 422 / 413）

迭代边界（本期不做）：标签（迭代 4）、投票/排序、评论、回答、编辑/关闭（迭代 5）、course_id、updated_at、列表/详情（2.5/2.6 下一分支）。

> 补测维度：NUL / lone surrogate / 递归炸弹等协议层畸形输入、方法路径变体、CASCADE 后活令牌、慢速攻击、100 并发。
> 脚本（仓库外）：`D:\a_work\bruteforce_24_extra.py`（20 用例）+ `D:\a_work\verify_24_findings.py`（独立仲裁，8 探针）。
> 首测结果：**16 PASS + 4 FAIL**（P-01~P-04，全是 500）；verify 8/8 复现，确认系统性（register/login 同陷）。

### 7.1 发现的缺陷（3 类根因）

1. **NUL 字节（P-01/P-02）**：标题/正文含 `\x00` 时无边界拦截，asyncpg 抛 `CharacterNotInRepertoireError: invalid byte sequence for encoding "UTF8": 0x00`，路由的 `except ValueError` 捕获不到（被 SQLAlchemy 包成 `DBAPIError`）→ **500**。
2. **lone surrogate（P-03，初判曾误归因 asyncpg）**：`json.loads` 成功、**Pydantic 已正确拦截**（`string_unicode`），但 FastAPI 默认 422 handler 回显非法 `input`，Starlette `JSONResponse` 以 `ensure_ascii=False` 编码含 surrogate 的回显体 → `UnicodeEncodeError` → **500**（栈在 fastapi/exception_handlers.py + starlette/responses.py）。
3. **递归炸弹 depth=2000（P-04，12KB 绕过 1MB body 上限）**：`json.loads` 成功、Pydantic 正确产出 3 个校验错误，但 `jsonable_encoder` 递归遍历回显的 2000 层 input（自递归近千次）→ `RecursionError` → **500**。

共同特征：响应无栈泄露（纯 "Internal Server Error"）、服务不崩、正常请求不受影响；但违反"畸形输入必须 4xx"口径。

### 7.2 修复（3 项，均经用户批准方案）

- **修 1（治 P-03/P-04）**：新增 [exception_handlers.py](file:///d:/a_work/CampusOverflow/app/shared/exception_handlers.py)，自定义 `RequestValidationError` 全局处理器，错误项只回 **type/loc/msg、绝不回显 input**；[main.py](file:///d:/a_work/CampusOverflow/app/main.py#L20) 挂载，覆盖所有端点。
- **修 2（治 P-01/P-02 及同类）**：新增纯标准库共享内核 [text_validation.py](file:///d:/a_work/CampusOverflow/app/shared/text_validation.py)，拒绝 C0 控制字符（放行 `\t\n\r`）与 U+D800~U+DFFF 代理码位（DEL/C1 可存储可编码，显示层风险归前端，不拦）。接入点：
  - 五个 VO 的 `__post_init__`：Title / Body / Email / StudentId / StaffId（ValueError 走既有路由 422 映射）；
  - [RegisterRequest](file:///d:/a_work/CampusOverflow/app/contexts/identity/interfaces/api/schemas.py#L23) / LoginRequest 的 `field_validator`。
  - **关键发现（实施时校正方案）**：注册用例的 `get_by_email / get_by_student_id / get_by_staff_id` 查重 SQL（register_use_case.py L26/L34/L41）**先于** VO 构造（User.register 在 L49），只靠 VO 拦 NUL 会先炸在 asyncpg——故 RegisterRequest 必须在 schema 边界拦截；login 的 identifier 直接进查询参数同理。questions 用例先 `Question.ask`（VO）后 `add`，VO 层即足够。
  - LoginRequest 只拒控制字符/代理字符、不碰格式：SQL 注入串（L-05）仍穿透到用例返回 401，已加集成测试钉死。
- **修 3（兜底）**：全局 `SQLAlchemyError → 400 JSON`，通用文案不含驱动/栈信息，异常详情仅写服务端 warning 日志。
