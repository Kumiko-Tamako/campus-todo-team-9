## Start（下个 Sprint 开始做的事）

1. **细案送审制**：3.6 声誉细案 v3.1 经三轮跨会话审计收敛，开工前自查抓到两个真
   隐患（celery_app 漏 include 任务模块→worker unregistered；R-08 预期值算错）。
   下个 Sprint 对复杂分支延续"先出细案、跨会话交叉审计、再开工"。
   （出处：3.6 台账评审采纳记录）
2. **暴力测试换方法轮**：同一功能面用正交方法多轮打——脚本化并发（1–8 路）→
   故障注入（8 路 PL/pgSQL 触发器）→ Unicode 等价类差分（10 路）→ 随机模糊+库级
   不变式对账（11 路）→ 白盒/直注入（13 路）。每轮换维度都抓到了前几轮漏网的
   （X-06 第九路、M3 恶意消息面第十三路首覆盖）。
   （出处：3.3/3.5/3.6 台账各节）
3. **跨会话交叉审计**：一个会话执行、另一个会话独立核验（门禁数字复跑、git diff
   核对、残留探针数据清点），防止"自报成绩"失真。
   （出处：3.6 第十三路"审计侧地面真值核验"）

## Stop（下个 Sprint 停止做的事）

1. **先写码后审计划**：3.1 开工前曾越权预写 domain 4 文件，最终全量回滚重写，
   纯浪费一轮。计划未批准 = 一行代码不写。
   （出处：PROGRESS 09-21/09-22 变更记录，"预写代码处置定为全量回滚重写"）
2. **轻信压测假象**：09-12"200 并发 PASS"实为客户端连接池上限 100 的假象，
   09-26 第四路才暴露真实瓶颈（NullPool 无界连接风暴）。压测工具本身要先验证。
   （出处：PROGRESS 09-26 第四路变更记录）
3. **修复积压"等用户"不登记**：多轮修复完成后停留工作区等提交，若没有 PROGRESS
   变更记录纪律，跨会话就会丢失"哪些已修未提"的状态。发现即登记，登记即完整。
   （出处：09-26/09-27 多条"未提交（等用户）"记录）

## Continue（下个 Sprint 继续做的事）

1. **六步法**（domain→application→infra→interfaces→测试→门禁）：分支 1–4 全部
   按此交付，domain 层 0 import 框架、上下文间 0 import 得到保持。
2. **最小权限执行**：每步只动点名对象，旁支问题只报不改（第八路 4 观察点先记录
   后另行批准修复，无一顺手改）。
3. **台账纪律**：docs/test/ 每功能一份，暴力测试逐路留档，PROGRESS 变更记录
   同步登记——本 Sprint 累计 13 路暴力测试全部可回溯。
4. **ADR 沉淀**：阶段 3 新增 ADR-003（连接池与容量）、ADR-004（声誉异步与
   Celery），重大决策离开聊天记录进仓库。
