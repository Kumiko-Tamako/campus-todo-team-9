## 一、功能概述

提问者（仅此角色）可采纳其问题下的某条回答为最佳答案：`Answer.is_accepted` 与 `Question.accepted_answer_id` **跨聚合双写、单 Session 事务**（任一侧失败整体回滚），一题一采纳（重复采纳含换答案一律 409），成功发 `AnswerAccepted` 事件（分支 4 声誉消费方留位）。登录用户可对问题/回答发表评论（正文复用 Body 值对象 1~5000 字），题评挂 Question、答评挂 Answer（aggregates.md L17 实体定性），按时间正序读取。详情顶层新增 `accepted_answer_id`（v3 裁定 #3）、`comments`（题评）与 answers 内嵌 `comments`（答评）。

接口：
- `POST /api/v1/answers/{aid}/accept`（204 / 401 / 403 / 404 / 409）
- `POST /api/v1/questions/{qid}/comments`、`POST /api/v1/answers/{aid}/comments`（201 / 401 / 404 / 422）
- `GET /api/v1/questions/{id}` 扩展：顶层 `accepted_answer_id` + `comments`，answers 元素内嵌 `comments`

迭代边界（本期不做）：声誉结算消费方（分支 4）、关闭态与"已关闭禁评"（v3 裁定 #2 随 Q08 迭代 5）、评论编辑/删除（backlog 无此故事）。

### 5.3 AC-12 并发抢采纳缺陷（发现 → 根因 → 修复 → 复测）★ 本分支核心发现

- **现象**：20 路并发采纳同一问题下 20 条不同答案，首跑 **16×204 + 4×409**——预期应仅 1 个成功。
- **根因**：`AcceptAnswerUseCase` 的"一题一采纳"检查是**应用层先读后写**（读 `question.accepted_answer_id` 为空 → 双写）。并发事务各自读到 NULL，全部通过检查，各自 UPDATE 不同答案的 `is_accepted=true` + `questions.accepted_answer_id`（最后写覆盖前者）→ 库里同题多条采纳，不变式被穿透。与投票一人一票不同：投票有复合唯一索引兜底，采纳当时**无任何库级约束**。
- **修复（与一人一票同模式：应用层检查 + 库级兜底）**：
  1. `answers` 表加**部分唯一索引** `uq_answers_one_accepted_per_question (question_id) WHERE is_accepted`——同一问题下 `is_accepted=true` 至多一行；
  2. `SqlAlchemyAnswerRepository.update` 捕获 `IntegrityError` → `AnswerAlreadyAcceptedError` → 409；
  3. 迁移 `7b8b074ad539` 先清理 AC-12 首跑遗留脏数据（每题保留最早一条采纳、对齐问题引用、孤儿引用置 NULL），再建索引；down→up 往返验证可逆。
- **复测**：AC-12 **1×204 + 19×409** PASS；qa 全量 201 passed 无回归。
- **意义**：这是阶段 3 首个**暴力测试发现并修复的真实并发缺陷**（分支 1 的 AV-12 是脚本缺陷）。印证"应用层检查必须配库级兜底"的纪律。

### 8.2 负载压测：**当前架构最高可持续并发 ≈ 100**（1w 并发不扛）

环境：单 uvicorn worker + `NullPool`（每请求新建 PG 连接）+ PG `max_connections=100`（实测确认）+ Docker VM 16C/8G；客户端 httpx `max_connections=12000` 真并发闭环。

| 档位（并发在途） | RPS | p50/p95/p99 | 结果 |
|:---|:---|:---|:---|
| 100 | 22 | 4.0s / 8.7s / 12.8s | **SUSTAINED**（零错误，但延迟已劣化，pgmax=78） |
| 150 | 23 | 5.9s / 21.9s / 23.2s | FAILED（29×5xx，pgmax=91） |
| 200 | 26 | 7.6s / 24.3s / 25.5s | FAILED（36×5xx，pgmax=87） |
| 300 | 31 | 7.7s / 32.8s / 34.3s | FAILED（54×5xx + 53 超时 + 144 连接失败，pgmax=92） |
| 一次性突发 200（复测） | — | p50 5.6s | **恰好 100×200 + 100×500**（与 max_connections=100 精确对应） |

隔离证据：`GET /health`（无 DB）50 并发 215 RPS 正常 → HTTP/应用层非瓶颈；`GET /questions` 顺序 66ms（其中 PG 新建连接 ~60ms）；50 并发即塌缩至 20 RPS。

**根因链（三项）**：
1. **NullPool 无界连接风暴**：`app/shared/engine.py` 刻意决策（pytest 多事件循环免疫，注释"阶段 4 上线前再评估"）——每请求新建 PG 连接、无复用无上限，并发在途≈同时连库数，>~95 触顶
2. **PG max_connections=100 打满** → `asyncpg.exceptions.TooManyConnectionsError`
3. **400 兜底有洞（新发现 F-2）**：该异常是 asyncpg 驱动裸异常（非 `SQLAlchemyError` 子类，SQLAlchemy 方言层 connect 不包装），`add_exception_handler(SQLAlchemyError, …)` 拦不住 → 裸 500（响应体无泄露，但状态码语义错误）

**历史 200 并发 PASS 的假象**：09-12 第七路 X-07「200 并发 GET 200×200」实为客户端默认连接池上限（100）压不出 >100 真并发；本轮客户端 `max_connections=12000` 才暴露真实承载。

**修复方向（未动任何代码，待批准）**：A. `NullPool`→`AsyncAdaptedQueuePool`（pool_size≈10-20+max_overflow 上界复用）+ 将 asyncpg 连接异常并入 400/503 兜底（代码改动，engine.py 注释已预留此决策点）；B. compose 调大 PG `max_connections`（治标）；C. 多 worker 会加剧连库争用，不可单独采用。1w 并发目标需 A+B+多 worker+压测复验，属阶段 4 容量工程范围。

**新发现与遗留（如实）**：
1. **多 worker 30s 级偶发挂起（未定位产品原因）**：多 worker 特有——100 档首轮 29/8425 个 30s 超时、300 档 70-100 个；同时段独立探针（直连同链路 asyncpg 连接 + SELECT 1）62-111ms 全程健康、PG 侧 81 连接全 idle、4 worker 进程存活且 Responding → 排除 DB/网络链路，卡在服务进程内部；**单 worker 全程 t/o=0 从未出现**。按 v3 预留口径降级：终测采用单 worker 口径；**生产（Linux 容器直连）复验前不建议 Windows 多 worker 用于容量验收**。
2. **1w 并发目标：初测口径（pool_timeout=10s）未达成，二轮已达成**——初测：单进程业务吞吐 ~150 RPS → 1w 在途排队（≈67s）远超 `pool_timeout=10s`；二轮以 `pool_timeout=120` + backlog=16384 + **分批预建连**达成 **10000 SUSTAINED**（见 8.4）。瓶颈本质 = 单请求 ~7ms 服务端处理；可承载并发 ≈ 吞吐 × 排队容忍度，非池、非 PG。
3. 池化实证增益（同等单 worker）：100 档 RPS 22 → 142（≈6.5×）；最高可持续并发 100 → 562（≈5.6×）；连接类错误语义 500 → 503（F-2 闭环）。

### 8.4 复测二轮（"其他方式"：排队容忍度杠杆 + 分批预建连）——**1w 并发在途 SUSTAINED 达成**

> "其他方式"= 不动产品代码，仅运行时参数 + 压测工具改造：`DB_POOL_TIMEOUT` 10→120s、uvicorn `--backlog` 2048→16384、单 worker 直连拓扑；压测脚本新增 CLI（`--levels/--seconds/--probe/--ramp/--read-timeout`）与连接错误分类、**pre-connect 两阶段模式**（每批 ≤2000 分批预建连、批间 1s，全部连好后统一开启测量窗口——建连与测量解耦，修复"建连风暴混入测量窗口"）。

**原理**：可承载并发 ≈ 吞吐 RPS × 可容忍排队时间。放宽 `pool_timeout`（10→120s）即放宽排队容忍度；吞吐未变（~240-374 RPS，pgmax 恒 51）。

| 档位 | 结果 | 关键数字 |
|:---|:---|:---|
| 5000（timeout=60、backlog=2048） | ✅ SUSTAINED | RPS 240、p99 45.8s、conn=0 |
| 8000（timeout=120、backlog=16384） | ✅ **SUSTAINED** | RPS 299；p50/p95/p99 = 57.7s/77.4s/79.3s；ok=8977；零错误 |
| **10000（+ pre-connect 分批预建连）** | ✅ **SUSTAINED** | **RPS 374；p50/p95/p99 = 72.5s/104.1s/107.4s；ok=11218；pre-connect 10000/10000 fail=0；零错误** |

**结论**：**1w 并发在途 SUSTAINED 达成**（零 5xx / 零传输错误 / 零超时 / 零非预期 4xx；延迟如实：p99 ~107s 为排队深度的真实反映）。未用 pre-connect 时，10k 同时建连的 SYN 风暴会撞 Windows 回环栈上限（ConnectionRefused）——**分批预建连完全化解**。

**方法学（二轮新增，务必遵守）**：
1. **pre-connect 两阶段优于 ramp**：ramp 把建连时间混入测量窗口且易与上轮拆连余波叠加；两阶段先全连上、再计时，10k 也能干净起步；
2. **轮间冷却**：大档拆连后 TIME_WAIT 可达数千-八千，须等归零（实测归零）再跑下一轮，否则污染（pgmax 51→21 是服务连接被掐的证据）；
3. 4 workers 在本机 Windows 环境 >1000 并发即连接层崩溃（accept 竞争，pgmax 远未触顶），单 worker 为本机最优——多 worker 仅在生产 Linux 复验。
